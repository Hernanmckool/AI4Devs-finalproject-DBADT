# HU-002 — Solicitud de reserva de alojamiento o tour

> **Prompt de origen:** §5, Prompt 1 — Definición de historias de usuario, en [`prompts.md`](../../prompts.md). Auditoría en [`validation-report.md`](validation-report.md) (§5, Prompt 2).
> **Fuente de decisiones aprobadas:** [`README.md`](../../README.md) §5 (HU-002) y §3.2 (`booking_requests`).
> **Alias:** `HU002` (nombre de archivo y `prompts.md`).
> **Estado:** historia aprobada; no implementada. Los identificadores `HU-002-Rxx` y `HU-002-Sxx` son **documentales y provisionales**: no son specs OpenSpec creadas ni ejecutadas (decisión C7).

## Historia

**Como** visitante de Descubre Barquisimeto,
**quiero** enviar una solicitud de reserva para un alojamiento o tour,
**para** manifestar mi interés y permitir que la agencia gestione y confirme mi solicitud.

## Objetivo y valor de negocio

Atiende NV-04 y NA-01 ([`prd.md`](../product/prd.md#2-análisis-de-necesidades)): el visitante expresa su interés con un formulario uniforme, **sin cuenta, sin pago y sin garantía de disponibilidad**, y la agencia recibe datos suficientes para contactarlo.

## Criterios de aceptación (aprobados)

| ID | Criterio |
|---|---|
| HU-002-R01 | El visitante puede solicitar una reserva sin registrarse ni iniciar sesión. |
| HU-002-R02 | El visitante puede seleccionar un alojamiento o tour activo. |
| HU-002-R03 | El formulario solicita nombre, correo electrónico, fecha y cantidad de personas. |
| HU-002-R04 | El teléfono y las observaciones son opcionales. |
| HU-002-R05 | Para alojamientos se requieren fecha de entrada y salida, y la salida debe ser posterior a la entrada. |
| HU-002-R06 | Para tours solamente se requiere la fecha prevista de realización. |
| HU-002-R07 | El sistema valida los datos obligatorios y muestra mensajes claros cuando existen errores. |
| HU-002-R08 | Al enviar una solicitud válida, el sistema la registra con estado `PENDING`. |
| HU-002-R09 | El visitante recibe un mensaje de recepción y un número de referencia. |
| HU-002-R10 | La recepción de la solicitud no implica disponibilidad confirmada ni genera un pago. |

## Escenarios Given / When / Then

Traducción documental de los criterios aprobados. Todavía no son archivos `.feature` ni pruebas ejecutadas.

```gherkin
Feature: HU-002 Solicitud de reserva de alojamiento o tour

  # HU-002-S01 — cubre R01, R02, R05, R08, R09, R10
  Scenario: Solicitud válida de alojamiento
    Given que el alojamiento seleccionado está activo
    And el visitante no ha iniciado sesión
    When envía nombre, correo, fechas de entrada y salida válidas y cantidad de personas
    Then la solicitud se registra con estado PENDING
    And recibe un mensaje de recepción con un número de referencia
    And el mensaje no confirma disponibilidad ni solicita un pago

  # HU-002-S02 — cubre R02, R06, R08
  Scenario: Solicitud válida de tour
    Given que el tour seleccionado está activo
    When el visitante envía nombre, correo, fecha prevista y cantidad de personas
    Then la solicitud se registra con estado PENDING
    And no tiene fecha de salida

  # HU-002-S03 — cubre R05, R07
  Scenario: Fechas de alojamiento inválidas
    Given que el visitante solicita un alojamiento
    When la fecha de salida es anterior o igual a la de entrada
    Then la solicitud es rechazada por validación con un mensaje comprensible
    And no se crea ningún registro

  # HU-002-S04 — cubre R02
  Scenario: Servicio no disponible
    Given que el alojamiento o tour está desactivado
    When el visitante intenta enviar una solicitud
    Then el sistema informa que el servicio no admite solicitudes nuevas
    And no se crea ningún registro

  # HU-002-S05 — cubre R03, R07
  Scenario: Datos obligatorios ausentes
    Given que el visitante completa el formulario de un tour activo
    When omite el correo electrónico
    Then el sistema indica que el correo es obligatorio
    And no se crea ningún registro

  # HU-002-S06 — cubre R04
  Scenario: Campos opcionales omitidos
    Given que el alojamiento seleccionado está activo
    When el visitante envía una solicitud válida sin teléfono ni observaciones
    Then la solicitud se registra con estado PENDING
```

## Reglas funcionales

RN-10 a RN-19 de [`business-flows.md`](../product/business-flows.md#42-bf-02--solicitud-de-reserva). Las principales:

- Exactamente un servicio por solicitud.
- `people_count` mayor que cero.
- Correo con formato válido y sin unicidad.
- Estado inicial `PENDING`.
- Recepción sin disponibilidad ni pago.

## Validaciones y comportamiento ante errores

| Situación | Respuesta API | Persistencia |
|---|---|---|
| Campos obligatorios ausentes o formato inválido | `400` | No |
| Ambos servicios o ninguno | `400` | No |
| Alojamiento sin salida, o salida ≤ entrada | `400` | No |
| Tour con fecha de salida | `400` | No |
| `people_count` ≤ 0 | `400` | No |
| Servicio inexistente o inactivo | `404` | No |
| Error interno | `500`, sin información sensible | No |

Códigos según [`api-reference.md`](../api/api-reference.md#4-reglas-de-validación).

## Dependencias y condiciones de implementación

- Contrato `POST /api/v1/booking-requests` aprobado.
- Tablas `booking_requests`, `accommodations` y `tours` con sus restricciones (TICKET-003).
- Datos sintéticos de alojamientos y tours activos e inactivos.
- Vistas de ficha de alojamiento o tour desde las que se inicia la solicitud (F02 y F03, sin contrato de API propio, A10).
