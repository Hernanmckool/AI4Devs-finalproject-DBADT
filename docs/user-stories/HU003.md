# HU-003 — Gestión de solicitudes de reserva

> **Prompt de origen:** §5, Prompt 1 — Definición de historias de usuario, en [`prompts.md`](../../prompts.md). Auditoría en [`validation-report.md`](validation-report.md) (§5, Prompt 2).
> **Fuente de decisiones aprobadas:** [`README.md`](../../README.md) §5 (HU-003), §2.5 y §3.2.
> **Alias:** `HU003` (nombre de archivo y `prompts.md`).
> **Estado:** historia aprobada; no implementada. Los identificadores `HU-003-Rxx` y `HU-003-Sxx` son **documentales y provisionales**: no son specs OpenSpec creadas ni ejecutadas (decisión C7).

## Historia

**Como** administrador de la agencia de turismo,
**quiero** consultar, filtrar y gestionar las solicitudes de reserva recibidas,
**para** confirmar o rechazar las solicitudes de alojamientos y tours y mantener actualizado su estado.

## Objetivo y valor de negocio

Atiende NA-02 a NA-04 ([`prd.md`](../product/prd.md#22-necesidades-operativas-de-la-agencia)): una bandeja controlada en la que solo el personal autorizado resuelve las solicitudes, con estados finales inmutables y sin resoluciones contradictorias entre administradores.

## Criterios de aceptación (aprobados)

| ID | Criterio | Contrato API |
|---|---|---|
| HU-003-R01 | El administrador debe iniciar sesión para acceder al panel de gestión. | `PATCH` (`401`) |
| HU-003-R02 | Únicamente los usuarios con rol `ADMIN` pueden consultar y gestionar solicitudes. | `PATCH` (`403`); la consulta no tiene contrato |
| HU-003-R03 | Se muestran identificador, servicio solicitado, fechas, cantidad de personas y estado. | **Sin contrato (A1)** |
| HU-003-R04 | El administrador puede filtrar por estado, tipo de servicio y fechas. | **Sin contrato (A1)** |
| HU-003-R05 | Puede consultar los datos de contacto y observaciones de cada solicitud. | **Sin contrato (A1)** |
| HU-003-R06 | Las solicitudes nuevas se muestran inicialmente en `PENDING`. | `POST` (HU-002) |
| HU-003-R07 | Una solicitud `PENDING` puede pasar a `CONFIRMED` o `REJECTED`. | `PATCH` (`200`) |
| HU-003-R08 | Las solicitudes `CONFIRMED` o `REJECTED` no admiten cambios posteriores. | `PATCH` (`409`) |
| HU-003-R09 | Ante cambios simultáneos de administradores, solo se aplica la primera actualización válida. | `PATCH` (`409`) |
| HU-003-R10 | El sistema informa los errores sin modificar indebidamente los datos registrados. | `PATCH` (todos los errores) |

## Escenarios Given / When / Then

Traducción documental de los criterios aprobados. Todavía no son archivos `.feature` ni pruebas ejecutadas.

```gherkin
Feature: HU-003 Gestión de solicitudes de reserva

  # HU-003-S01 — cubre R02, R03, R04, R06 (sin contrato de API, A1)
  Scenario: Consulta de solicitudes pendientes
    Given que existen solicitudes en PENDING, CONFIRMED y REJECTED
```

## Validaciones y comportamiento ante errores

| Situación | Respuesta API |
|---|---|
| Sin credenciales válidas | `401` |
| Rol distinto de `ADMIN` | `403` |
| `id` no es UUID o `status` no permitido | `400` |
| Solicitud inexistente | `404` |
| Solicitud ya resuelta, o carrera perdida | `409` `INVALID_STATUS_TRANSITION` |
| Error interno | `500` |

En ningún caso de error cambia el estado registrado (R10).

## Dependencias y condiciones de implementación

- Mecanismo de autenticación decidido (ADR-P01, A5).
- Contrato aprobado de consulta y filtrado (A1). Sin él, R03–R05 y S01 no pueden implementarse ni probarse por API.
- Contrato `PATCH /api/v1/booking-requests/{id}/status`.
- Solicitudes creadas por HU-002.
